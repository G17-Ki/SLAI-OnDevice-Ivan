# F2 — The ES/FR ASR route

## Decision

**Option (b): Parakeet-TDT-0.6B-v3 INT8 on the CPU provider, inside the existing
runtime companion.** Option (a) — a separate exact-2.40 QNN process — is the follow-up,
not tonight's demo.

Stated plainly, as the lane brief asks: **for a demo tonight, (b) is the right answer,
and (a) is the follow-up.** But (b) is not free, and the honest headline is not "ES/FR
now works fast on CPU". It is:

> Spanish and French now have a real, offline, on-device recognizer with correct
> native-script output. It runs on the CPU, it claims no acceleration, and in the
> current process-per-request architecture each ES/FR turn pays a model-load cost that
> the existing five languages do not. Projected phone cost per ES/FR turn is
> **7–11 seconds `PROJECTED`**, of which **6–9 s `PROJECTED`** is model load, not decoding.

If a ten-second Spanish turn is not filmable, the fix is named in §6 and it is a
half-day of work, not a research problem.

## 1. Why not (a), in one paragraph

The three published SM8850 Parakeet contexts Lane E verified embed exact QNN
`2.40.0.251030114326_189385` (`out/e/E3.json:94`, header strings in all three binaries).
The programme pins `2.45.0.260326154327` (`out/e/E5.json`). The runtime companion
*already* hosts a QNN 2.40 provider for SenseVoice
(`AsrHttpServer.java:229-231`, `libQnnHtp.so` from its own `nativeLibraryDir`), so the
Parakeet contexts are version-compatible with **that specific process** — and this is the
one place the "just load them, they're both 2.40" argument is tempting.

It is still wrong for tonight, for a reason that has nothing to do with version numbers:
Lane E's registry rule is *exactly one QNN runtime provider per APK/process*
(`out/e/artifact_registry.json` → `runtime_provider_policy.rule`), and the programme pin
is 2.45. Shipping a second 2.40-pinned NPU consumer inside the accepted companion would
make the companion's QNN version an accident of which model loaded first, and would put
the *accepted* EN/ZH/JA/KO SenseVoice route at risk on the night it is being filmed. The
four probe packages in `android-app/*-probe/` exist precisely so that a new QNN consumer
gets its own package, its own `nativeLibraryDir`, and its own version. That is option (a),
and it deserves its own acceptance run.

**Nothing in this lane loads a QNN context. No `.bin` context is pushed, installed, or
referenced by any new code path.**

## 3. What I measured

`HOST`. Apple M2, macOS 15.4.1 arm64, Python 3.11.11, sherpa-onnx 1.13.4, CPU provider,
`nemo_transducer`, greedy search, 16 kHz / 80-dim features, `--num-threads=2` (the same
thread count the proven Russian Zipformer route uses at `AsrHttpServer.java:285`).
Full record: `artifacts/f2_parakeet_cpu_reference.json`.

Inputs are the vendor demo clips shipped inside the model archive, resampled once to the
app's canonical contract (44-byte RIFF, PCM16, mono, 16,000 Hz — `AsrHttpServer.java:494`)
because the vendor files are 22,050/24,000 Hz and the server rejects them as shipped.
The file I measured is byte-identical to the file the bundle installs.

| Lang | Fixture | Bytes | Duration | RTF median (n=5) | RTF range | Same text 5/5 |
|---|---|---:|---:|---:|---|---|
| **es** | `asr_es_parakeet_vendor.wav` | 170,572 | 5.329 s | **0.195** | 0.136–0.235 | yes |
| **fr** | `asr_fr_parakeet_vendor.wav` | 159,054 | 4.969 s | **0.135** | 0.133–0.158 | yes |
| en | `asr_en_parakeet_vendor.wav` | 123,086 | 3.845 s | 0.165 | 0.149–0.372 | yes |
| de | `asr_de_parakeet_vendor.wav` | 88,094 | 2.752 s | 0.200 | 0.185–0.260 | yes |

Transcripts (these become the installer's ES/FR parity assertions):

- **es** — `No preguntes qué puede hacer tu país por ti, pregunta qué puedes hacer tú por tu país.`
- **fr** — `Ne vous demandez pas ce que votre pays peut faire pour vous. Demandez-vous plutôt ce que vous pouvez faire pour lui.`
- en — `Ask not what your country can do for you, ask what you can do for your country.`
- de — `Alles hat ein Ende, nur die Wurst hat zwei.`

Correct accents, correct punctuation, correct native script, byte-stable across five
repeats per language. Peak RSS for the whole measuring process was 879,149,056 bytes.

An earlier run of the identical script recorded ES 0.093 / FR 0.103. The difference is the
machine, not the model: this Mac carried load average 29–53 on eight cores throughout the
measurement window, with unrelated applications holding 40–90% CPU. Repeats of the same
command differed by more than 2× here and by up to 7× in the F3 harness.

**Treat every absolute host timing in this lane as contaminated.** The honest host band is
**0.09–0.24** and the decision in §1 does not depend on where in it the truth sits.

Two things load cannot change, and they are the two things this section is actually for:

1. **The transcripts were byte-identical across every repeat of every run**, in all four
   languages. That is what makes them usable as the installer's parity assertions.
2. **The ratio** in the next subsection — session creation costing several times the
   decode it enables — is a property of doing a 652 MiB graph deserialization per request.
   Contention scales both terms.

### The number that decides the architecture

The companion spawns `libasrrunner.so` **once per request** and lets it exit
(`AsrHttpServer.java:294-352`). So I measured a whole cold process, three times, with the
model file already hot in the page cache:

| | run 1 | run 2 | run 3 |
|---|---:|---:|---:|
| interpreter/library import | 0.116 s | 0.137 s | 0.185 s |
| **ONNX Runtime session creation** | **4.150 s** | **4.443 s** | **5.568 s** |
| decode (5.329 s of audio) | 0.843 s | 1.643 s | 1.380 s |
| **total wall** | **5.123 s** | **6.243 s** | **7.143 s** |

Page cache was warm for all three, so ~4–5.5 s is **ONNX Runtime graph deserialization of
a 652 MiB INT8 encoder**, not disk. Warming the file does not remove it. In the current
architecture every ES/FR turn pays it. This is the single most important fact in F2 and
it is why §6 exists.

The same contention caveat applies to the absolute seconds here. What does not depend on
load is the *shape*: session creation is four to five times the decode it enables, and no
amount of warming changes that, because the cost is per-process and the process is new
every request.

## 4. Projected phone latency — `PROJECTED`

The only host↔NX809J anchor this project owns is
`reports/android_phone/streaming_response/tts_research_20260726/evidence/device/device_vs_host_main.json`,
`device_vs_host_rtf_speedup` (`PRIOR`): host RTF ÷ device RTF over n=72 onnxruntime-CPU
runs on this exact phone, median **0.748**, min **0.554**; restricted to the 24 Supertonic
rows, median **0.642**, min 0.554, max 0.834. Values below 1 mean the phone is slower.

| Quantity | Host measured | Divisor | Phone `PROJECTED` | Transfer confidence |
|---|---:|---|---|---|
| ES decode RTF | 0.195 | 0.642 … 0.554 | **0.30 – 0.35** | medium — same runtime, same provider, different model family |
| FR decode RTF | 0.135 | 0.642 … 0.554 | **0.21 – 0.24** | medium |
| ES decode, 5 s utterance | 1.04 s | | **1.6 – 1.9 s** | medium |
| Session creation per request | 4.15 – 5.57 s | 0.642 … 0.554 | **6 – 9 s** | **low** — the anchor is a compute ratio and session creation is deserialization plus allocation, not matmul |
| **Total per ES/FR turn, ASR only** | 5.1 – 7.1 s | | **7 – 11 s** | **low** |

Add TTS on top: F3 measured Supertonic ES/FR at host RTF 0.68–2.93, and the phone
already produces Supertonic RU/JA/KO final chunks at 290–584 ms (`PRIOR`,
`PRIORITIZED_MODEL_SWEEP.md:115`).

Nothing above is `AIHUB-PROFILED`, `BENCHMARK` or measured on a phone. No phone was
connected. Two independent weaknesses stack in this table: the host inputs were measured
under heavy CPU contention (§3), and the anchor transfers a compute ratio onto a
deserialization cost it was never derived from. Treat the whole table as an
order-of-magnitude statement. It exists to answer one question — "is an ES/FR turn about
one second, about ten, or about a minute?" — and the answer is **about ten**.

What would replace it: the two round-trip times `verify_esfr.sh` prints on the phone. That
single command turns this entire table into a measurement.

## 5. What was changed to implement (b)

Six edits, all additive, none touching the accepted EN/ZH/JA/KO/RU path.

| File | Change |
|---|---|
| `android-app/runtime-companion/.../AsrHttpServer.java` | `es`/`fr` branch in `recognize()`; new `runParakeet()` and `parakeetArtifactsReady()`; `parakeet_v3_cpu` health row; error text now lists nine selections |
| ″ | `complete`/`artifacts_complete` **deliberately keep their old meaning** (the five accepted languages) so `install_app_owned_runtime.sh` still gates on the accepted stack; ES/FR readiness is reported as new `esfr_artifacts_ready` / `esfr_complete` keys |
| `android-app/app/.../demo-ui/index.html` | `PARAKEET_CPU_LANGUAGES` / `COMPANION_AUTO_LANGUAGES` / `COMPANION_ASR_SELECTIONS` constants; ES/FR branch and Latin-script check in `selectCompanionAsr()`; ES/FR rows in `plannedAsrFacts()`; honest `npu_fallback_reason`; the companion gate now admits ES/FR |
| ″ | Selector labels now read "Spanish (CPU)" and "French (CPU)" |
| `scripts/test_streaming_audio_ui.mjs` | New ES/FR assertions: backend, provider, `npu_gate: "blocked"`, fail-closed on a dead Parakeet backend, rejection of non-Latin output, and that auto never routes to ES/FR |
| `android-app/app/.../tts/CandidateRegistry.kt`, `stage_device_bundle.py`, two TTS host gates | F3's half; see `F3.md` |

`runParakeet()` is deliberately shaped exactly like `runRussian()`: same
`libasrrunner.so`, `--provider=cpu`, `--num-threads=2`, `--decoding-method=greedy_search`,
no `--model-type` (sherpa-onnx detects `nemo_transducer` from the encoder's ONNX metadata
— verified on host), and **no QNN argument anywhere on the path**. The raw WAV is passed
through unpadded; `fixedQnnWav()`'s ten-second zero-padding is SenseVoice-only and would
have made Parakeet decode 4.7 s of silence.

Three deliberate restrictions:

1. **`auto` never routes to ES/FR.** The auto ladder runs `qnn-auto` and then `ru`; adding
   Parakeet would load 652 MiB on every ambiguous turn. Spanish and French are an explicit
   selection. The ambiguity error message now says so.
2. **ES/FR fail closed.** Only English falls back to LFM2.5-Audio if the companion errors
   (`index.html`, `requestTranscript`). A Parakeet failure surfaces as a Parakeet failure
   rather than being silently re-attributed to LFM.
3. **Italian is untouched** and still falls through to the LFM CPU path. It was in the
   language selector before this lane and it is not in scope.

## 6. The follow-up that removes the 6–9 seconds

Ranked, with the reason each is or is not tonight's answer.

1. **Persistent in-process recognizer via the sherpa-onnx AAR** — the model is loaded once
   and every later turn costs only decode (`PROJECTED` 1.6–1.9 s for 5 s of Spanish).
   `com.k2fsa.sherpa.onnx.OfflineRecognizer` and `OfflineTransducerModelConfig` are already
   in `sherpa-onnx-1.13.4.aar`, which the **main app already links** for TTS — verified by
   `javap`. The blocker is not code, it is library layout: the runtime companion packages
   its own `libonnxruntime.so` from the sherpa QNN build, and the AAR ships a different
   `libonnxruntime.so` under the same name. That collision is the same class of problem
   that created the two-APK split (`runtime-companion/README.md:36-42`) and it needs to be
   resolved deliberately, not at 9 p.m. **Half a day, not a research problem.**
2. **Option (a), the isolated exact-2.40 Parakeet package** — highest fidelity, matches the
   artifact Lane E verified, and `android-app/supertonic-probe/` is a four-file template
   for it. Needs its own APK, its own acceptance run, and a decision about whether a
   2.40-pinned package may exist beside a 2.45 programme pin.
3. **A smaller multilingual CPU recognizer** (Whisper base/small INT8 is roughly a fifth of
   the size and is already probed in `android-app/whisper-probe/`) — would cut session
   creation proportionally at a quality cost. **Unmeasured in this lane; listed, not
   recommended.**
4. **Thread tuning.** 2 threads beat 4 on the M2 here, but the NX809J has a different core
   layout and this was never measured on it. One line in `runParakeet()`.

## 7. What this does not establish

- No phone was connected. Every phone number above is `PROJECTED`.
- No word error rate. Four vendor demo clips with correct output is not an accuracy
  measurement; it is an integration proof.
- No noisy, accented, far-field or conversational Spanish or French was tested.
- No QNN context was loaded, and no claim of ES/FR acceleration is made anywhere in the
  code, the health payload, or the UI. `plannedAsrFacts("es").npu_gate` is the string
  `"blocked"` and the reason names the exact version conflict.
