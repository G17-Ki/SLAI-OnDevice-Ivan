# A1 — Qwen3-ASR-0.6B: tied or untied `lm_head`?

**Verdict: TIED. `EXACT`.** Stack M's ASR row is **782,426,112**, not 938,008,576.

## What I did

`Qwen/Qwen3-ASR-0.6B @ 5eb144179a02acc5e5ba31e748d22b0cf3e303b0`, `model.safetensors`
(1,876,091,704 B, 612 tensors, all BF16). Header read over HTTP Range: 8 bytes for the
u64 header length (74,544), then 74,544 bytes for the JSON tensor map. No weights
downloaded.

Both tensors exist on disk at distinct, adjacent, non-overlapping offsets:

| tensor | dtype | shape | data_offsets | bytes |
|---|---|---|---|---:|
| `thinker.lm_head.weight` | BF16 | [151936, 1024] | 372752384 – 683917312 | 311,164,928 |
| `thinker.model.embed_tokens.weight` | BF16 | [151936, 1024] | 683917312 – 995082240 | 311,164,928 |

151,936 × 1,024 = **155,582,464** — exactly the Qwen-family token-embedding matrix, and
exactly the disputed delta. So the tie is *materialised* in this export: the question is
not whether two tensors exist, it is whether they hold the same values.

## The byte comparison

Three passes, escalating:

1. **33 sampled 64 KB blocks** spread evenly across both 311 MB regions → 33/33 identical,
   0 differ.
2. **Full-region streaming SHA-256** of both data regions — 100% coverage, 622,329,856 B
   streamed and hashed, nothing written to disk → the two digests are equal, zero
   mismatching chunks.
3. **`config.json` at the pinned revision** → `thinker_config.text_config.tie_word_embeddings = true`.

The config is corroboration, not the basis. The byte comparison is the measurement.

## Adjudication

Reports **A and B were right; report C was wrong**, and its `EXACT` label was unearned.

C's figure, 938,008,576, is precisely what the HuggingFace API returns for
`safetensors.total` on this repo. That number is a sum of `prod(shape)` over the on-disk
tensor map with **no tensor-identity de-duplication**. On a repo that materialises a tie
it is the *serialized* basis. Reading it as a parameter count produces "untied" and looks
authoritative because it came from an API.

I hit the identical trap a second time in the same lane: `Qwen/Qwen3-0.6B` reports
751,632,384 from the same API, byte-compares as **TIED**, and is 596,049,920 unique —
the same 155,582,464 delta, on the same tensor shape. That independently confirms Stack H
row H3.

**Rule of thumb worth carrying:** any Qwen-family repo whose HF API total exceeds
config-derived arithmetic by exactly `vocab_size × hidden_size` is a materialised tie
until byte-compared.

## What I could not close

The verdict is about the **upstream safetensors checkpoint**. An ONNX / QNN / GGUF export
may re-materialise the tie, so a shipped artefact could carry 938,008,576 *on disk* while
the model has 782,426,112 unique parameters. This is not hypothetical — in A3 I found
exactly this duplication in MOSS-TTS-Nano's ONNX export, where one embedding table is
materialised three times.

Class: `UNKNOWN`. Closing experiment: initializer enumeration of the sherpa-onnx INT8
export of Qwen3-ASR-0.6B, de-duplicated by external-data `(location, offset, length)`.
The method is implemented and demonstrated in `tools/onnxr.py`.

It does not move the ledger, because S-2 counts the unique basis.
