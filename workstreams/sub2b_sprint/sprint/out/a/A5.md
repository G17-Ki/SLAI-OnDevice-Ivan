## FE-1 — OmniASR cannot emit punctuation. This is the finding.

`facebook/omniASR-CTC-300M`'s sentencepiece tokenizer is **character-level and contains
zero punctuation tokens.**

Exhaustive byte scan of the whole 87,562 B `omniASR_tokenizer.model`:

```
'.' 0    ',' 0    '?' 0    '!' 0    ';' 0    ':' 0
'a' 2    'e' 1    'n' 2    'o' 1        CJK: present   Cyrillic: present
```

The pieces are single Unicode characters (CJK, Greek, Khmer, Georgian, Cyrillic…). Digits
are present. So the scan is sound, not a decode failure.

`EXACT`, and **architectural** — this is not a vendor claim about behaviour, it is the
absence of the tokens from the vocabulary. A CTC head cannot emit a symbol its vocabulary
does not contain.

§2.4a said a punctuation row for Q is "*more* likely to be non-zero than for D". It is
stronger than that: **the row is mandatory**, and neither Q nor F can afford the cheapest
neural option that exists.

**The only affordable resolution is to delegate punctuation and ITN to the backbone LLM**
— zero additional parameters, because Qwen2.5-1.5B / Falcon-H1-1.5B are already in the
ledger and already generating text. That works. But it is a **binding architectural
constraint**, and it must be written into the build-time assertion rather than assumed.
Hence: Q and F are **UNVERIFIED**, not COMPLIANT.

Worth noting the irony: **TH-60 forbids promoting Q while any front-end cell is
`UNKNOWN`, and names g2pW as the hazard.** g2pW is avoidable — rows Q7/F7 already specify
rule-based pypinyin. The unavoidable row was the one sized at zero.

## FE-2 — D's zh/en punctuation row closes at zero

`FunAudioLLM/SenseVoiceSmall`'s model card, verbatim:

> `use_itn`: Whether the output result includes punctuation and inverse text normalization.

Punctuation and ITN are **in-model**, inside the 233,999,167 already counted. Zero
additional parameters.

§2.3 row D11 was `UNKNOWN` for all five languages. It is now **0 for zh/en**, and
`UNKNOWN` only for es/fr/ru (row D11b, parakeet's token set — a ~20-minute check).

## FE-3 — §2.2 is refuted: Silero does not bundle a stress marker

§2.2 states the RU stress marker is "bundled inside Silero TTS as `silero_stress`
(undisclosed count, and the reason L6's bound is 100,000,000 rather than 20,000,000)".

It is not bundled. The `v5_cis_base` `torch.package` archive's module constructor takes
`accentor=None`, and no accentor tensors exist among its 317 storages.

Two consequences: the stated justification for the 100,000,000 bound does not hold (the
measured count is 22,850,584), and **L is missing an RU stress row it believed it already
had.** Rule-based (eSpeak NG `ru` + marked-stress lexicon) costs 0; RUAccent-class costs
~12,500,000 `CLAIMED`. L's headroom absorbs either. But it must be a row.

## FE-4 — g2pM may be redundant in L

Magpie's `model_config.yaml` declares its own `ChinesePhonemesTokenizer` +
`ChineseG2p` (rule-based pinyin) for the zh route. If the shipped route uses it, row L7's
401,548 is a duplicate. Small, but it is exactly the kind of row that gets shipped twice.

## FE-5 — D and M delete the G2P ladder entirely

D's front end is genuinely almost free: pypinyin (0), eSpeak `ru` stress rules (0),
Supertonic's built-in phonemisation for en/es/fr/ru (0), SenseVoice native ITN (0).
M's is smaller still — MOSS needs **no external G2P for any of the five languages**, so
its only open front-end row is punctuation.

§2.4 calls this "one of the few real arguments for M". The inventory supports it.

## The comparison was not like-for-like — and it favours D

The lane brief notes that Stack D carried no front-end row while L carried g2pM, so the
two were not being compared on equal terms. Resolved in both directions:

- **D**'s low row count reflected *reality*, not an omission. D8/D9/D10 are genuinely 0,
  and D11 is now 0 for zh/en.
- **L**'s g2pM row may be redundant (FE-4), and L is *missing* an RU stress row it
  wrongly believed was bundled (FE-3).

**D's front end is cheaper than L's, not less well documented.**
